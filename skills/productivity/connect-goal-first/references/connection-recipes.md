# Connecting accounts and services: methods and recipes

Reference for `connect-goal-first` (drop in as `references/connection-recipes.md`). The SKILL.md stays the plain-words, goal-first flow; this file is the "how" once the goal is agreed. Distilled from real setups; paths are examples, not defaults.

## How to work (preferences that held up)
- **Do the clicking yourself.** If a browser on this Mac is signed in to the right account, drive the setup console directly instead of handing the person a list of steps. Hand off only what truly needs them: their credentials, a 2FA code, a consent click, a Keychain master-password prompt, a physical approval.
- **Discover accounts; don't ask for them.** Mine browser history for the accounts the person actually uses, show the list, and let them exclude some.
- **Personal over work.** Create OAuth projects under the personal account, never a work org's project, so employer admins can't see or revoke them. Skip work accounts unless asked. For work accounts, suggest macOS Internet Accounts (Mail, Calendar, Contacts) when the admin is likely to block unverified apps.
- **Prefer self-owned OAuth to hosted connectors** (Composio, Pipedream, Zapier): tokens stay local. Mention the hosted option only as an alternative. When asked "how can I give you access to X", give concrete options with a recommendation, free/self-hosted first, then build it.
- Pause for approval before each irreversible submit in a console wizard. Run steps as short, separately verified commands so approvals are quick to grant.
- The person is often away from the Mac (on their phone). Anything needing a physical click at the Mac (macOS privacy permissions, unlocking a password manager) is deferred, not attempted. Approval prompts time out in about a minute: batch many steps into one command; on a timeout stop, summarise done/remaining, and ask for "go".
- **Verify with a real read** per account or service (list calendars, read a balance) before reporting success.

## 1. Inventory first
- `hermes plugins list` (set `COLUMNS=250` to avoid wrapping), `grep -A40 mcp_servers $HERMES_HOME/config.yaml`, `/Applications`, existing skills. Report: working / installed but unconfigured / available.
- Ask which platform before recommending device-specific integrations (Apple apps are low value without an iPhone).

## 2. Find the person's accounts from browser history
- Copy the profile's `History` SQLite file to scratch first (the browser locks the live file), query `urls` by domain/title, then delete the copy. Chrome-epoch times: `last_visit_time/1000000-11644473600`.
- Profiles: Chrome `~/Library/Application Support/Google/Chrome/<Profile>/`, Arc `~/Library/Application Support/Arc/User Data/<Profile N>/`; names are in `Local State` → `profile.info_cache`.
- Gmail addresses seen: `sqlite3 COPY.db "select title from urls where url like '%mail.google.com%' and title like '%@%';" | grep -oE "[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[a-z]{2,}" | sort | uniq -c | sort -rn`.
- Can't recall which service/account they used: also search past agent transcripts and session history, their notes (project notes often name the tool) and Gmail (welcome/billing mails). Try "Sign in with Google" with their main account before concluding no account exists.

## 3. Google accounts (all of them, one OAuth client)
- The bundled `google-workspace` skill owns the token scripts and API usage. Run its scripts with a Python that has the Google libraries. Multi-account: `GOOGLE_ACCOUNT=<email>` gives a per-account token at `$HERMES_HOME/google_tokens/<email>.json`. The scripts read `HERMES_HOME`: set that, never fake `HOME`.
- Build the Cloud Console side in the signed-in browser (selectors below): create the project, enable the APIs in one flow, External consent screen, add every account as a test user, **publish to In production**, then create the Desktop client and pass its JSON to `setup.py --client-secret <path>`.
- Publish before signing accounts in: apps left in Testing get refresh tokens that expire after 7 days, and tokens minted under Testing keep that expiry after publishing (re-authorize them). Publishing needs homepage + privacy URLs on a domain the person owns. Explain "publish" plainly if asked: no store listing, data only flows to their Mac.
- Authorize each account: `GOOGLE_ACCOUNT=<email> setup.py --auth-url` (current versions take no `--services`/`--format` flags; grep the `https://accounts.google.com...` URL from its output and append `&login_hint=<email>`), approve in the browser, then `--auth-code` and `--check`, one account at a time.
- When the person must paste a list of emails into a Console chip field, give ONE code block, space-separated on one line.
- For multi-inbox searches, one account per call with simple queries; big OR-query loops time out.

### Cloud Console selectors (proven)
1. **Project:** `https://console.cloud.google.com/projectcreate`. Set `#p6ntest-name-input` (native value setter, then `input` and `blur`), read `Project ID: xxx` from the page text, click `Create`. The console then redirects to the *last used* project: keep the ID you read.
2. **APIs:** `https://console.cloud.google.com/flows/enableapi?apiid=gmail.googleapis.com,calendar-json.googleapis.com,drive.googleapis.com,sheets.googleapis.com,docs.googleapis.com,people.googleapis.com&project=<ID>`. `Next`, `Enable`, wait ~25 s for "You have successfully enabled".
3. **Consent screen:** `https://console.cloud.google.com/auth/overview/create?project=<ID>`. App name `input[formcontrolname=displayName]`; support email: click `[formcontrolname=userSupportEmail]` then the matching `[role=option]`; audience radio value `external`; contact email chip input (aria-label "Text field for emails"): set the value then an Enter keydown; terms checkbox; `Create`. Click only visible `Next` buttons (`b.offsetParent`): every wizard step has one.
4. **Test users + publish:** `https://console.cloud.google.com/auth/audience?project=<ID>`, add test users, Publish app → In production.
5. **Client:** `https://console.cloud.google.com/auth/clients/create?project=<ID>`, Desktop app, save the JSON (0600, never printed).

## 4. OAuth flows and MCP servers
- Start the CLI flow, open its authorize URL in the signed-in browser, click Allow, and harvest the `localhost` redirect from `Page.getNavigationHistory`. Match on the OAuth `state` param, never just "the latest redirect". Write codes/secrets to 0600 files from a script; never print them.
- **MCP server with OAuth:** `hermes mcp add <name> --url <url> --auth oauth --connect-timeout 300` as a background pty process; poll it, open the printed authorize URL, approve, then answer `Enable all N tools? [Y/n/select]` via process submit. Verify with `hermes mcp test <name>`. Tools appear only in the next turn/session: say so. The default 30 s connect timeout expires before an approval finishes, and "save anyway" may not persist the entry.
- **npx-based MCP installers that reject the Node version:** check what the person's interactive shell resolves, not the agent's PATH: `zsh -ic 'cd <dir>; which -a node; node -v; mise current node'`. A `.tool-versions` in the cwd can pin an old Node via mise/asdf: `mise use nodejs@<supported>` there (or one-shot `mise exec node@<v> -- npx …`); an already-open terminal may keep the old shim until a new shell / `hash -r`.
- **Multi-client MCP installers:** run `--dry-run --all-detected --yes --format json` first to see the planned config writes, then apply with the same flags and parse `appliedActions`. A non-zero exit / `needs_human` can just mean optional extras remain: read `remediation` before calling it failed. After they write `config.yaml`, the gateway needs a restart; don't restart while a gateway chat is mid-turn (an unclean restart pauses that session). Inside One, don't restart it yourself: say so.

## 5. Driving the person's browser for setup
- `browser_exec(local=true)` only attaches to a Chromium default browser (Chrome, Edge, Brave, Chromium). If the default is Arc, check whether it already exposes CDP (`lsof -nP -iTCP -sTCP:LISTEN | grep -i arc`, usually :9222) and drive it over CDP; that session has their logins. Open your own tab (`curl -s -X PUT "http://localhost:<port>/json/new?<url>"`), never take over theirs. Popups (e.g. Google's account chooser) open as NEW targets: find them in `/json/list`.
- Confirm which account is signed in before changing anything (Google: `[aria-label*="@"]` gives `Account: Name (email)`).
- Angular/Material consoles: set inputs with the native `HTMLInputElement.prototype.value` setter, then dispatch `input`, `change` and `blur`; plain `.value=` is ignored. JS `.click()` and synthetic Enter often do nothing: use CDP `Input.dispatchMouseEvent` / `Input.insertText`. Re-list inputs after every navigation (element IDs carry a per-load prefix).
- Credential pages: never dump `aria-label`s or button labels (copy buttons embed the full secret); mask secret patterns (e.g. `GOCSPX-…`) in every eval. Masked key inputs stay masked in `.value`: real-click the page's "Copy to clipboard", read `pbpaste` inside a script that writes straight to a 0600 file or `.env`, clear the clipboard, and verify the key against the service's API.
- Before clicking a destructive button, confirm by DOM that it sits in the intended row and that the confirm dialog names the intended object; a page-level "Delete" often deletes the parent resource.
- No saved login? Look for a one-tap remembered profile on the site's login page first; never type passwords: use the password-manager path below.
- macOS has no `timeout` binary; commands wrapped with it silently don't run.

## 6. Passwords and 2FA
- Built-in `browser_vault` supports 1Password and Bitwarden. Don't push paid password managers: point to free tiers first.
- **KeePassXC users:** a small bridge can fill logins without secrets ever entering chat, logs or memory. Design rules that worked:
  - CLI: `/Applications/KeePassXC.app/Contents/MacOS/keepassxc-cli` (bundled; not on PATH), called with `-q -k <keyfile>` and the master password piped on stdin from the macOS Keychain. The person sets that Keychain item himself with `security add-generic-password -a <account> -s <service> -U -w` (hidden prompt), so it never passes through chat. Check presence without reading it: `security find-generic-password -a <account> -s <service> >/dev/null && echo PRESENT`.
  - Read-only: never write the .kdbx (sync conflicts with their phone). Secrets go straight from keepassxc-cli into the page via CDP `Input.insertText`; return only `filled <field> (<n> chars)`.
  - Origin check before every fill: https only, and the page host must equal or be a subdomain of the entry's URL host. Entries without a URL fall back to a title-keyword map (gmail → google.com, instagram → instagram.com …); no match → refuse. Extend the map; never drop the check.
  - `kp_list()` shows entry path, username, URL and a TOTP flag, no secrets; copy entry paths verbatim (titles can carry trailing spaces). TOTP via KeePassXC (right-click → TOTP → Set up), then `keepassxc-cli show -t` generates codes: no need to ask for 2FA.
  - `ls -R -f` lists `Recycle Bin/` and `[empty]` lines: filter them or `show` fails.
  - `Invalid credentials … (HMAC mismatch)` after the person "updates entries" means the file's credentials changed (or a different DB was saved over it), not corruption. Check size/mtime and other .kdbx files, ask which credentials open it now, wait for the Keychain update. Never restore or overwrite files yourself; their sync service's version history is the recovery path.
  - Recommend a dedicated limited DB, password + key file (key file outside the synced folder), no YubiKey (a physical tap breaks unattended unlocks). If they choose to expose their full vault on the Mac, follow their choice without re-arguing; recommend a minimal DB before the bridge ever leaves the Mac.
  - Google's sign-in rejects headless browsers after the email step ("This browser or app may not be secure") however credentials are filled: test on Google in a real or non-headless profile. Google's identifier field is `#identifierId` (type=text), password `input[type=password][name=Passwd]` after `#identifierNext`.

## 7. Remote browser (optional)
- Architecture that fit: the assistant, the password bridge, keys and secrets stay on the Mac; ONLY the browser runs remotely (e.g. Browserbase), so nothing opens on screen. Don't propose moving the assistant itself off the Mac unless asked. Browserbase's free tier (5-minute sessions, about 1 browser-hour a month) is too small for long jobs.
- Setup: sign up with "Continue with Google" in a background tab (account-chooser rows need a real mouse click at the email's coordinates); keys on Settings → General are masked even after "Show": use the copy-button + `pbpaste` route into `.env` (0600); verify with `curl -s -o /dev/null -w '%{http_code}' https://api.browserbase.com/v1/projects/$BROWSERBASE_PROJECT_ID -H "X-BB-API-Key: …"` → 200; add `cloud_provider: browserbase` under `browser:` in config.yaml (back it up first); env `BROWSERBASE_API_KEY`, `BROWSERBASE_PROJECT_ID` (`BROWSERBASE_KEEP_ALIVE` defaults true). The running gateway keeps its startup config until a restart, which cuts the current chat: get their OK first.
- Verify by IP, not by config: open `https://api.ipify.org?format=json` in browser_exec and compare with `curl https://api.ipify.org` from the Mac; same IP = still local. A `ws://127.0.0.1:…` CDP URL proves nothing (local proxy). The cloud browser has none of their cookies: logins come from the bridge (filled from the Mac over CDP) or persisted contexts.

## 8. The assistant as its own chat bot (Hermes gateway)
Use the built-in gateway adapter, with the assistant as its OWN bot identity, never acting as the person. Docs: https://hermes-agent.nousresearch.com/docs/user-guide/messaging/<platform>.
- A platform turns on just by its env vars in `$HERMES_HOME/.env` (e.g. `TELEGRAM_BOT_TOKEN`, `SLACK_BOT_TOKEN` + `SLACK_APP_TOKEN`); no `platforms:` block is needed. Always set the allowlist var (`SLACK_ALLOWED_USERS`, `TELEGRAM_ALLOWED_USERS`) to the owner's platform user ID, or the gateway denies everyone. Behaviour via `hermes config set`, e.g. `slack.unauthorized_dm_behavior ignore` (default `pair` offers strangers a pairing code), `slack.require_mention true`.
- The gateway reads platforms only at start: after the .env edit it needs a restart (inside One, don't restart it yourself: say so). Back up `.env` first, append from a script that reads the token files, delete the scratch token files, and check with `grep '^SLACK_' .env | sed 's/TOKEN=.*/TOKEN=<set>/'`.
- **Slack (Socket Mode):** (1) `HERMES_HOME=<home> hermes slack manifest --agent-view --name <Bot> --description "..." --write <home>/slack-manifest.json`; (2) find the workspace and the account that owns it, sign in in the hidden browser; (3) create the app with `https://api.slack.com/apps?new_app=1&manifest_json=<urlencoded compact JSON>`, cutting `features.slash_commands` to a few (/new, /stop, /help) because the full manifest is "Request-URI Too Long" (DMs and @mentions don't need slash commands; `!cmd` works in threads); (4) pick the workspace in `#manifest_team_and_input_workspace_select` (Next stays disabled until you do), Next, Create; the URL becomes `app.slack.com/app-settings/<TEAM>/<APP>/general`; (5) Basic Information → "Generate Token and Scopes": name `hermes-socket`, scope `connections:write`, Generate; regex `xapp-[A-Za-z0-9-]+` inside the page script into a 0600 file; (6) `.../install-on-team` → "Install to <workspace>" → Allow; regex `xoxb-...` off the success page into a 0600 file; (7) verify before touching .env: `auth.test` (bot token: ok, team, bot user), `apps.connections.open` (app token: proves Socket Mode), the owner's member ID via `users.info` or the admin member table, and `conversations.open users=<owner>` + `conversations.history` (proves the bot can read its own DM; sends nothing); (8) write the env vars, set the config keys, save the `my-connections/<name>` skill, add to `connections.json`, tell the owner a restart is needed and ask them to DM the bot for the live test.
- Finding the workspace: `curl -s -o /dev/null -w '%{http_code}' https://<guess>.slack.com/` (403 = exists, 404 = doesn't); open hits and read "Sign in to <Name>". "<email> doesn't have an account on this workspace" means try the next signed-in Google account; try EVERY one before asking or handing off a robot check (the email path triggers reCAPTCHA; Google sign-in doesn't). `https://<ws>.slack.com/admin` lists members with Member ID, email and role (Primary Owner is usually the owner). Slack billing/welcome mails (`from:slack.com`) show which address registered a workspace.
